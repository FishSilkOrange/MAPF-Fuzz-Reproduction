## 当前规模与论文规模

论文主实验采用 128×128 地图、100 个智能体；PIBT/HCA/PIBT+ 每次运行 1 小时、20,000 个任务，LaCAM* 每次 6 小时、25,000 个任务；每种求解器重复五次，fuzzer 使用 32 个进程。

`reproduce/README.md` 中的正式预检示例使用 128×128、50 个智能体、10 个任务组；根目录 README 另给了 32×32、20 个智能体的小样例。这些都不是论文主实验配置，适合先在租用服务器检查运行和产出。脚本默认值更小（8×8 空地图、4 个智能体、3 组），用于快速启动，不用于论文结果对比。实际使用的值写入每次运行的 `manifest.json`。

## 小规模会不会改变种子

会。这里的“种子”是 MAPF 测试实例，不只是随机数：地图、障碍布局、智能体起终点和后续变异都属于实例内容。

- 地图缩小后，整个地图被重新采样到较小网格，通道宽度、障碍形状、连通区域都会变化。
- 智能体数量改变后，起终点集合、拥堵程度、求解轨迹和热点也会变化。
- 因此即使随机数 `--seed` 相同，小地图/少智能体生成的初始任务和后续种子池也不会等同于论文规模。

在 `--mode mutate` 下，测试步骤仍保持相同：生成或变异任务 → 求解器执行 → 蜕变任务执行 → 验证解并计算 SOC/MD → 计算特征和 fitness → 将符合口径的任务及轨迹派生反馈放入后续变异池并优先选择最高 fitness。完整轨迹在提取热点、等待和 critical 信息后不驻留内存；对应可重放文件目前保存在任务目录。初始 OF 可入池，初始 CF/异常任务不入池；后续变异的 OF/CF 任务不入种子池，但有效原任务仍可进入新颖度索引。变化的是每个任务的规模和难度，不是流程步骤。

## 建议的服务器运行顺序

1. 用 32×32、20 agents 跑几组，确认环境和文件输出。
2. 固定地图和随机种子，逐步升到 64×64/50 agents、128×128/50 agents。
3. 再切换到论文规模 128×128/100 agents，运行多次并记录配置。
4. presentation 明确区分“小规模流程验证”和“论文规模实验”，不要把两者的发现数直接作公平比较。
